# Autonomous TCR–pMHC model research — initial objective

## Task

You are an autonomous ML research agent. Your goal is to improve prediction of whether a T-cell receptor (TCR) binds a peptide–MHC (pMHC) complex, using **amino-acid sequence inputs only**.

**`ml.py` is the only existing source file you may modify.** It contains the initial, intentionally simple model and training implementation. Treat it as the starting point, not an architectural constraint. You have full freedom to replace or redesign the model architecture, feature representation and optimisation approach **within `ml.py`**, including MLPs, CNNs, transformers, attention, protein language model encoders or representation-learning objectives, subject to the available compute and libraries. Do not alter the underlying dataset, splits, evaluation definitions or experimental runner.

**Editable surface during autonomous research: `ml.py` and one append-only log, `experiments/evaluation.log`, only.** Create that log and its parent directory if absent; do not create additional source files, summaries, JSON ledgers or context files. `eval.py`, `final_eval.py`, this objective, the controller, dependencies and datasets are read-only to the research agent. Existing training outputs such as `model.pth` may be generated by executing `ml.py`; this is not permission to edit other files manually. Configure training within `ml.py` to append its training events to the same shared log instead of overwriting a separate training log. Do not overwrite or delete previous log entries.

Use scientific best practice to improve the model: formulate falsifiable hypotheses, make controlled changes, check implementation validity and interpret the complete evaluation evidence. You may choose the architecture, representation, optimiser and training loss. The loss used to train a model is distinct from the fixed, comparable validation loss computed by `eval.py`. Do not change the evaluation protocol to improve the apparent score.

Decisions must consider validation loss together with overall AUROC, AUPRC, peptide-level and category-specific performance, class counts, possible overfitting and computational cost. No single metric automatically determines acceptance. Prioritise credible generalisation evidence, and justify trade-offs explicitly in the log. A small change in a small subgroup is not sufficient evidence of improvement; use repeat seeds for promising or ambiguous results within budget.

## Fixed evaluation contract

Run training using the existing entry point, then evaluate the saved checkpoint:

```bash
python ml.py
python eval.py --experiment_dir experiments/1/ --experiment-id EXP_0001 --hypothesis "Specific falsifiable hypothesis" --change "Exact change made to ml.py"
```

Use the actual checkpoint directory if it differs from the starter default. `eval.py` creates/appends `experiments/evaluation.log` automatically. Use this same log path for every experiment; do not create a separate history per run. Read the entire evaluator report before interpreting results.

Preserve the existing interface while redesigning internals: `ml.Model()` reconstructs the saved model and `forward(peptide, hla, tcr)` returns one finite binding probability in [0, 1] per row; `ml.Dataset(path)` exposes `.data` in original CSV row order and returns `(peptide, hla, tcr, binding_flag)`. Keep input columns and labels in `.data` unchanged. The fixed evaluator selects eligible full-chain rows itself and independently checks returned labels against the CSV. Training in `ml.py` must use the same eligibility checks. Use full sequences without truncation: inspect the dataset padding lengths and preserve the starter masking behaviour; negative padding must never crop long sequences. Architecture freedom does not include silently changing row membership, targets or the evaluator interface.

`eval.py` reports:

- Overall AUROC (ROC AUC), AUPRC (average precision), accuracy at threshold 0.5, MSE/Brier score and binary log loss. `validation_loss` is the fixed, sample-weighted probability MSE; this remains comparable even if the training loss changes. It is not a requirement to train with MSE. Binary log loss clips probabilities to [1e-7, 1-1e-7].
- The same metrics **for each peptide**, with row counts, positive/negative counts and prevalence; unweighted peptide-macro AUROC and AUPRC across peptides with both labels, plus coverage/exclusion counts.
- The same metrics **for every supplied category value**, preserving its name (for example unseen TCR, unseen HLA or completely unseen). It recognises common category column names; use `--category-column COLUMN` if the name differs or multiple candidates exist. Missing annotations are reported as a group. If no category column is available, this limitation is explicit.
- When `TRAIN_PATH` is available, separately derived overlapping seen/unseen groups for TCR, peptide, HLA and pMHC, fully seen components, unseen TCR plus unseen pMHC, and strictly completely unseen TCR/peptide/HLA. These use exact sequence identity against eligible full-chain training rows, irrespective of label. TCR identity is the ordered full alpha/beta pair, HLA identity is the supplied HLA sequence, and pMHC identity is the peptide/HLA-sequence pair. Strict completely unseen means all three components are unseen. Do not assume the supplied categories have these definitions; report the supplied and derived groups separately. Unseen combinations are not necessarily unseen individual chains or alleles.
- Undefined AUROC/AUPRC as `null` with a reason for empty or single-class groups; never substitute 0.5 or omit inconvenient categories.
- Cohort counts, evaluation runtime, model/evaluator/checkpoint/data hashes and errors. Runtime is evaluation time, not training time; record measured training time separately in the shared log.

Agent evaluation records execution validity, whether a hypothesis/change was provided, comparable previous runs, validation-loss improvement and AUROC change relative to previous best values. These are evidence about execution and outcomes, not a judgement of scientific reasoning. Metrics are compared only across matching data/evaluator protocols. The evaluator records `pending_agent_interpretation`; the agent then appends its own decision and reasoning. A lower MSE is not an automatic keep decision.

**Never evaluate test data in the autonomous optimisation loop.** Validation is the default. Final test evaluation requires an explicit authorised final step with `--split test --allow-final-test`, after model and preprocessing selection is frozen. Do not feed final test results back into further model selection. External IMMREP results must also remain outside iterative optimisation; labels already influenced by IMMREP relabelling cannot support claims of an untouched independent IMMREP benchmark.

## Running the controller

From the repository root, use the existing project environment with its dependencies installed. Set `GEMINI_API_KEY` (or the existing supported Gemini authentication), `TRAIN_PATH` and `VALIDATION_PATH` in the environment or repository `.env`. `TEST_PATH` is not needed by this loop. Run only inside the operator-approved local or scheduler allocation; the controller does not submit remote jobs or allocate a GPU.

```bash
# Inspect local data and eligibility without calling Argon or training.
python agent/agent.py --dry-run

# First proof of concept: baseline setup plus one autonomous modification.
python agent/agent.py --max-experiments 2 --run-timeout 900

# Continue the same history and restore the selected source/checkpoint identity.
python agent/agent.py --resume --max-experiments 2
```

Use `uv run python` in place of `python` if that is how the existing project environment is launched. The controller defaults to `gemini-4-argon`; override `--model` only with the exact model identifier supplied by your provider. There is no silent fallback to another model. Use `--category-column COLUMN` for a non-standard category field.

The starter `ml.py` now validates complete alpha/beta inputs, selects full-chain training/validation subsets, pads without cropping and masks padding during pooling. The first experiment verifies the baseline setup, preserving its architecture and loss. Subsequent experiments test scientific changes. Model proposals contain complete replacement code for `ml.py`; Argon receives no shell tools. The controller syntax-checks proposals, runs fixed subprocess commands with timeouts, and checks hashes of protected source files and configured training/validation data. These checks are not an OS sandbox for executing Python; use the existing isolated workspace and permitted data access.

The default budgets are two experiment attempts, eight API calls (including token counting; four calls per complete experiment), 900 seconds per training/evaluation process, 600 seconds per API request, and one hour for the session. Increase `--max-api-calls` explicitly when requesting more than two experiments. Input context is counted before generation; exceeding `--max-input-tokens` stops the loop rather than truncating the history. API errors or invalid responses stop safely and restore the incumbent source. Training/evaluation failures are logged and returned to Argon for interpretation when the remaining API/time budget permits.

Functions in `agent/agent.py` separate responsibilities:

| Function | Responsibility |
| --- | --- |
| `inspect_environment` | Validate local inputs and provide aggregate schema/cohort statistics |
| `build_context` | Load objective, evaluator, current source and full history |
| `propose_experiment` | Ask Argon for one hypothesis, rationale and replacement `ml.py` |
| `apply_model_change` | Syntax-check and update only `ml.py` |
| `run_training` | Execute `ml.main()` with a unique checkpoint directory and seed |
| `run_evaluation` | Execute fixed validation evaluation and verify the resulting report |
| `decide_next_action` | Ask Argon to interpret the full history and justify a decision |
| `restore_or_keep` | Promote a kept model; otherwise restore the incumbent source |
| `run_agent_loop` | Coordinate bounded experiments, logging, recovery and the shared-log lock |

Each experiment gets a generated checkpoint directory under `experiments/`; all proposals, source revisions, decisions and metrics remain in the one shared log. No separate source backups or summary files are created. The selected checkpoint path is printed at completion and recorded in the log. `discard` and `investigate` restore the incumbent source; follow-up experiments may reconstruct a prior candidate from its logged source. `--resume` verifies the protocol and selected checkpoint hash and restores the corresponding `ml.py`. An interrupted proposal remains in the history; it is never silently treated as accepted. Run only one controller per shared history; concurrent controllers are rejected through a log lock.


## Stopping, saving models and final test evaluation

The controller always has finite experiment, session-time, subprocess-time, API-call and input-context limits. It also stops after `--patience` consecutive `discard`, `investigate` or `failed` decisions (default 3). Patience uses the agent's justified promotion decisions across all validation evidence; it is not an automatic MSE-only acceptance rule. Each resumed invocation has a fresh explicit budget and patience counter, while the full experimental history is retained.

```bash
# Example bounded search: at most 10 attempts / 40 API requests / two hours.
python agent/agent.py --max-experiments 10 --max-api-calls 40 --session-timeout 7200 --run-timeout 900 --patience 3

# From a second terminal in the same checkout, request a stop.
python agent/agent.py --request-stop
```

Alternatively press Ctrl+C in the controller terminal. Stop requests are checked between decisions and while a training/evaluation process is running. An in-flight API request returns or reaches its timeout before a logged stop can be acted on. Child processes receive SIGINT and have up to ten seconds to save before forced termination. SIGTERM to the controller follows the interruption path as well.

Each experiment has its own generated checkpoint directory, including discarded/inconclusive experiments. The starter `ml.py` atomically saves `initial_model.pth` after model creation, `last_model.pth` every epoch and during graceful interruption, and `model.pth` for the epoch with the lowest validation loss within that training run. `eval.py` evaluates `model.pth`; cross-experiment selection remains scientifically justified across all metrics. Preserve this checkpoint contract when editing `ml.py`. Do not delete previous experiment checkpoints. The controller records a checkpoint inventory and hashes after each training attempt. Source/configuration revisions are already stored in the shared log, so no additional source backup files are needed.

The latest partial checkpoint is not automatically a valid or selected model. A failure before model creation cannot produce weights; a forced kill, failed save or power failure can retain only the last completed disk save. The controller restores incumbent `ml.py` on stopping and records the selected checkpoint location.

Once research has stopped, evaluate a chosen frozen model on your labelled test CSV:

```bash
# Default: the last scientifically kept model.
python final_eval.py --test-path /absolute/path/to/test.csv

# Or explicitly choose a validation-evaluated saved experiment.
python final_eval.py --test-path /absolute/path/to/test.csv --experiment-id SESSION_0001
```

The CSV must provide the same sequence/length/label columns required by `eval.py`; optional category annotations are supported. Use `--category-column COLUMN` if necessary. `TRAIN_PATH` (or `--train-path`) supplies the original training reference for derived novelty groups. Final evaluation reuses the fixed full-chain eligibility and metric functions: overall, per-peptide, peptide-macro and supplied/derived category metrics. `test_loss` is the test MSE; shared subgroup fields retain the evaluator's existing `validation_loss` key but are explicitly labelled as test-split measurements.

`final_eval.py` loads the model's exact recorded source in memory and verifies its checkpoint hash, instead of assuming that current `ml.py` still matches every historical architecture. It does not alter current `ml.py`, train, or call Argon. It refuses to run while a controller holds the log lock, or if the supplied CSV is identical to a recorded training/validation file. Results append to the existing log.

Starting final evaluation marks this research history as finalized, even if inference then fails. The controller refuses further autonomous optimisation on that history, so final test results cannot be fed into subsequent model selection. Re-running final evaluation for technical verification is possible, but these results must never be used to select another model; a benchmark remains exposed after the first read. Keep the existing history rather than deleting test records to circumvent this restriction.


## Argon context window and thinking settings

`agent/agent.py` is the Python controller; Argon is the remote decision model called through `google.genai.Client().models.generate_content`, with `gemini-4-argon` as the default model ID. This is real API orchestration code, not the previous joke/demo call. Successful live execution still depends on valid credentials, provisioned model access, installed dependencies and local data paths; mock tests do not verify those external conditions.

The controller explicitly sends `thinking_config={"thinking_level": "high"}` by default. Override with `--thinking-level low|medium|high`. It does not send deprecated `thinking_budget`, sampling overrides (`temperature`, `top_p`, `top_k`) or explicit `cached_content`.

The full objective, evaluator, current source and complete log are supplied for each proposal and interpretation. Default input cap is 900,000 tokens, leaving room within Argon's shared 1,048,576-token window for the schema margin and up to 65,536 thinking/output tokens. Input is counted before each generation. Exceeding the configured input cap or shared-window budget stops the loop without truncating history. Actual input capacity depends on the combined request: the entire 1M window cannot simultaneously be filled with input and a full output budget.

`--max-output-tokens` includes thinking as well as the final JSON/code answer. The synchronous controller supports up to 65,536; it deliberately rejects larger values. Generating beyond 65,536 requires the background/long-decode API and its polling lifecycle, which this controller does not implement. Background generation is not needed just to send a large input history. Requests allow 600 seconds by default (`--api-timeout`), still bounded by remaining session time. API response token-usage metadata and finish reasons are logged; truncated responses are rejected rather than applied as partial code.

```bash
python agent/agent.py --max-experiments 2 --thinking-level high --max-input-tokens 900000 --max-output-tokens 65536 --api-timeout 600
```
